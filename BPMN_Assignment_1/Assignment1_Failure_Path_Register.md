# Failure Path Register

Model: [`Assignment1_BPMN_Diagram.bpmn`](Assignment1_BPMN_Diagram.bpmn) · Diagram: [`Assignment1_BPMN_Diagram.png`](Assignment1_BPMN_Diagram.png)

Every row below maps to elements that exist in the diagram. Labels in the last column are the exact `name` values in the BPMN file; a flow label is written as *gateway → "branch label"*. Limits are enforced by the conditions on the gateway branches (visible in the XML as `conditionExpression`).

Lane abbreviations: **STU** Student / Team · **COORD** Project Coordinator · **COMM** Review Committee (incl. HoD) · **GUIDE** Faculty Guide · **PMS** Project Management System.

## Register

| ID | Failure point (process step) | Trigger / cause | Detection mechanism | BPMN construct | Recovery / resolution | Retry / deadline limit | Final outcome | Diagram labels |
|---|---|---|---|---|---|---|---|---|
| **F1** | Proposal validation (PMS) | Missing fields, no abstract, invalid roll numbers | Service task produces an error list; exclusive gateway tests the result | Service task + exclusive gateway (3 branches) + bounded loop + escalation to a user task | Error list is returned and the team resubmits. After the second failed attempt the case is escalated to the coordinator, who either resolves the errors (flow continues to the team-rule check) or closes the proposal | Max **2** submission attempts (`submissionAttempts < 2`), then escalation | Continues to team check, **or** end "Closed – invalid proposal data" | `Validate Proposal Data` → `Data complete & valid?` → "No – return error list (attempts < 2)" / "No – 2 attempts used: escalate" → `Resolve Escalated Proposal Errors` → `Errors resolved?` → `Closed – invalid proposal data` |
| **F2** | Team-rule check (PMS) | Team size above the limit, or a member already belongs to another team | Business rule task (decision table) returns invalid | Business rule task + exclusive gateway + send task + **error end event** | Team is notified of the violated rule and the submission is closed as invalid. The team re-forms and starts a new submission (new process instance) | No retry inside the instance | End "Invalid team" (error end event) | `Check Team Rules` → `Team rules satisfied?` → "No – size limit / member in another team" → `Notify Team of Rule Violation` → `Invalid team` |
| **F3** | Similarity / duplicate-topic check (PMS → COORD) | Similarity score above the threshold against earlier projects | Service task returns a score; exclusive gateway compares it with the threshold | Service task + exclusive gateway + user task + exclusive gateway (3 branches) | Coordinator reviews the match and records the outcome in the same task. Outcomes: cleared (false positive) → committee review; modified topic required → team is sent the reasons and loops back to submission; reject → proposal closed | Max **1** topic modification (`topicModifications < 1`); a second "modify" outcome is routed to rejection | Continues to review, loops to resubmission, **or** end "Rejected – duplicate / plagiarised topic" | `Run Similarity / Duplicate-Topic Check` → `Similarity above threshold?` → "Yes" → `Review Similarity Match & Record Outcome` → `Coordinator decision?` → "Cleared" / "Modify topic (first time)" / "Reject (or topic already modified once)" → `Send Reasons & Invite Topic Resubmission` / `Rejected – duplicate / plagiarised topic` |
| **F4** | Proposal submission (STU) | Team does not submit before the deadline | Interrupting **timer boundary event** on the submission task (`timeDate = submissionDeadline`) | Timer boundary event + message intermediate throw event + user tasks + timer boundary + exclusive gateway | Team is flagged and notified. The team may submit a late-submission request, which the coordinator approves (back to submission with an extended deadline) or refuses | One extension only (`extensionsGranted < 1`); late request must arrive within **3 days** | Back to submission, **or** end "Lapsed – deadline missed, no late request", **or** end "Lapsed – late submission refused" | `Submission deadline reached` → `Team flagged & notified of missed deadline` → `Submit Late-Submission Request` (boundary `3 days: no request`) → `Decide Late-Submission Request` → `Late submission approved?` → "Approved (one extension only)" / "Refused" |
| **F5** | Committee review (COMM) | Committee asks for revision (scope too large, vague objective, weak novelty) | Decision recorded in the user task; exclusive gateway routes it | Exclusive gateway + revision loop + interrupting timer boundary event | Team revises and resubmits; the proposal returns to the committee | **7-day** revision deadline; max **2** revision cycles (`revisionCount < 2`). After that the "revise" branch is no longer available, so the committee must approve or reject | Back to review, **or** end "Lapsed – revision deadline missed", **or** F6 path once the limit is reached | `Committee decision?` → "Revision requested (cycles < 2)" → `Revise & Resubmit Proposal` (boundary `7 days: no revision`) → `Lapsed – revision deadline missed` |
| **F6** | Committee review (COMM) | Committee rejects (not feasible, out of syllabus, lacks resources) or the revision limit is exhausted | Exclusive gateway on the recorded decision | Exclusive gateways + send task + loop to start | Reasons are sent to the team. One new-topic submission is allowed: the flow loops back to the submission task with a new deadline. A second rejection is final | Max **1** new-topic submission (`newTopicSubmissions < 1`) | Loop to submission, **or** end "Rejected – reasons sent to team" | `Committee decision?` → "Rejected (or 2 revision cycles used)" → `New-topic submission still allowed?` → "Yes – one new topic" → `Send Reasons & Invite Topic Resubmission`; "No" → `Rejected – reasons sent to team` |
| **F7** | Committee review (COMM) | Committee does not decide within the SLA | Two timer boundary events on the review task | **Non-interrupting** timer boundary (reminder) + **interrupting** timer boundary (escalation) + user task for the HoD | After 5 days a reminder is sent while the review task stays open. After 10 days the review task is cancelled and the HoD decides; the HoD decision joins the normal decision gateway | Reminder at **5 days**, escalation at **10 days** | Decision is always produced (by committee or HoD) | `Evaluate Proposal` boundaries `5 days: no decision` → `Reminder sent to committee`; `10 days: still no decision` → `Decide Escalated Proposal (HoD)` → `Committee decision?` |
| **F8** | Guide matching (PMS) | Domain mismatch, or all matching guides at maximum load | Business rule task returns "none"; exclusive gateway tests it | Business rule task + exclusive gateway + user task + exclusive gateway | Coordinator allocates a guide manually, appoints a co-guide or external guide, or places the team on the waiting list | Single manual decision, no loop | Continues to allocation, **or** end "Closed – team on guide waiting list" | `Match Guide by Domain & Workload` → `Eligible guide found?` → "No – "none" (domain mismatch / max load)" → `Allocate Guide Manually` → `Guide assigned?` → "Yes – manual / co-guide / external" / "No – waiting list" → `Closed – team on guide waiting list` |
| **F9** | Guide response (GUIDE) | Guide declines (workload, conflict of interest) or does not respond | Exclusive gateway on the response; interrupting timer boundary event for silence | Timer boundary event + exclusive gateways + service task + bounded loop | The guide is excluded from the candidate pool, the attempt is counted and the matching rule is re-run. After three unsuccessful attempts the coordinator allocates manually (same task as F8) | **5 days** to respond; max **3** allocation attempts (`allocationAttempts < 3`) | Next guide is asked, **or** manual allocation | `Accept or Decline Guide Request` (boundary `No response in 5 days`) / `Guide response?` → "Declined" → `Attempts < 3?` → "Yes – try next guide" → `Exclude Guide & Count Attempt` → `Match Guide by Domain & Workload`; "No – 3 attempts used" → `Allocate Guide Manually` |
| **F10** | Recording the allocation and notifying the team and guide (PMS, sub-process) | Database write error or e-mail/notification service down | **Error boundary events** on the service task and on both send tasks | Collapsed sub-process containing error boundary events, retry loops with timer back-off, error end events; error boundary event on the sub-process; user task fallback | Each failing step waits 5 minutes and retries. When any step has used its retries, an error end event terminates the sub-process; the error boundary on the sub-process routes to the coordinator, who records the allocation and informs the parties manually | Max **3** retries per step (`dbRetries`, `teamNotifyRetries`, `guideNotifyRetries` `< 3`), 5-minute wait between retries | Allocation is recorded (automatically or manually) and the process continues | Sub-process `Record Allocation & Notify Parties`: `Write Allocation Record` (boundary `Database write error`) → `DB retries < 3?` → `Wait 5 min` / `Recording failed`; `Notify Student Team` and `Notify Faculty Guide` (boundary `Notification failure`) → `Retries < 3?` → `Wait 5 min` / `Team notification failed` / `Guide notification failed`. Main level: boundary `Retries exhausted` → `Record Allocation & Notify Parties Manually` |
| **F11** | After allocation, during the confirmation window (PMS) | Team dissolves / withdraws, or the guide becomes unavailable (leave, resignation) | **Event-based gateway** waiting for a withdrawal message, a guide-unavailability message, or the window timer | Event-based gateway + message catch events + **compensation** (throw events, compensation boundary event, compensation handler task) | Compensation undoes "Allocate Guide & Reserve Slot" by running "Release Guide Slot". On withdrawal the withdrawal is recorded and the project closed. On guide unavailability the team returns to the guide-matching step | Events accepted until the **7-day** confirmation window closes | End "Withdrawn – guide slot released", **or** reallocation, **or** (no event) end "Project allocated & confirmed" | `Await confirmation window` → `Team withdrawal received` → `Release guide slot` → `Record Withdrawal & Close Project` → `Withdrawn – guide slot released`; `Guide unavailable` → `Release guide slot` → `Match Guide by Domain & Workload`. Compensation: boundary `Undo allocation` on `Allocate Guide & Reserve Slot` → `Release Guide Slot` |
| **F12** *(additional)* | Similarity check (PMS) | Similarity service is unavailable (technical error) | **Error boundary event** on the service task | Error boundary event + exclusive merge + user task | The proposal is not blocked: it goes to the same coordinator review task as F3, where originality is judged manually and the outcome recorded | No automatic retry; one manual review | Same three outcomes as F3 | `Run Similarity / Duplicate-Topic Check` boundary `Similarity service unavailable` → `Review Similarity Match & Record Outcome` |
| **F13** *(additional)* | Waiting for the guide's answer (GUIDE) | Team withdraws after approval but before a guide has accepted | Interrupting **message boundary event** on the guide's task | Message boundary event + message end event | The pending guide request is cancelled. No slot has been reserved yet, so nothing needs compensating | — | End "Withdrawn – guide request cancelled" | `Accept or Decline Guide Request` boundary `Team withdrawal received` → `Withdrawn – guide request cancelled` |

## Bounded loops at a glance

| Loop | Counter (branch condition) | Limit | What happens at the limit |
|---|---|---|---|
| Validation resubmission (F1) | `submissionAttempts < 2` | 2 attempts | Escalation to `Resolve Escalated Proposal Errors` |
| Late-submission extension (F4) | `extensionsGranted < 1` | 1 extension | `Lapsed – late submission refused` |
| Topic modification (F3) | `topicModifications < 1` | 1 modification | `Rejected – duplicate / plagiarised topic` |
| Committee revision (F5) | `revisionCount < 2` | 2 cycles, 7 days each | Decision is treated as rejection (F6 path) |
| New topic after rejection (F6) | `newTopicSubmissions < 1` | 1 new topic | `Rejected – reasons sent to team` |
| Guide allocation attempts (F9) | `allocationAttempts < 3` | 3 attempts | `Allocate Guide Manually` |
| DB write / notification retries (F10) | `dbRetries`, `teamNotifyRetries`, `guideNotifyRetries` `< 3` | 3 retries each | Error end event → `Record Allocation & Notify Parties Manually` |
| Reallocation after guide unavailability (F11) | none (needs an external message each time) | Ends when the 7-day window timer fires | `Project allocated & confirmed` |

|---|---|---|---|
| Success | `Project allocated & confirmed` | None end | Happy path |
| Rejected | `Rejected – reasons sent to team` | Message end | F6 |
| Rejected | `Rejected – duplicate / plagiarised topic` | Message end | F3, F12 |
| Invalid | `Invalid team` | Error end | F2 |
| Invalid | `Closed – invalid proposal data` | Message end | F1 |
| Lapsed | `Lapsed – deadline missed, no late request` | Message end | F4 |
| Lapsed | `Lapsed – late submission refused` | Message end | F4 |
| Lapsed | `Lapsed – revision deadline missed` | Message end | F5 |
| Unallocated | `Closed – team on guide waiting list` | Message end | F8, F9 |
| Withdrawn | `Withdrawn – guide request cancelled` | Message end | F13 |
| Withdrawn | `Withdrawn – guide slot released` | Message end | F11 |
| (side branch) | `Reminder sent to committee` | Message end | F7 – ends only the non-interrupting reminder token, not the process |
| (sub-process) | `Allocation recorded & parties notified` | None end | Normal sub-process completion |
| (sub-process) | `Recording failed`, `Team notification failed`, `Guide notification failed` | Error end | F10 – caught by boundary `Retries exhausted` |

## Assumptions

The brief fixes the 2-attempt validation limit, the 7-day revision period, the 2 revision cycles, the single new-topic submission, the 3 allocation attempts and the 3 retries. The following values are not given in the brief and are assumptions of this model: committee SLA of 5 days (reminder) and 10 days (escalation); 5 days for a guide to respond; 3 days to file a late-submission request; one late extension; one topic modification after a similarity match; 5-minute wait between technical retries; a 7-day confirmation window after allocation.
